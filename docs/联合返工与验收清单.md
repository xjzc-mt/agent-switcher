## P1 · 发布前必须修复

### A1 · 连续写入长凭据可能清空 Keychain

在 macOS 26.6.2 的真实隔离钥匙串中，首次写入 8,000 字节成功，第二次更新超时，原值变成 0 字节。当前先置空已有项，再调用 Security.framework 写新值；恢复时又把空项当作受保护的未知格式。修改 `writeRawKeychain` 和 `restoreSnapshot`，区分更新与新建，消除先置空的窗口，完整凭据始终不进入进程参数。[Keychain 适配器](../src/antigravity-native.ts)

- [ ] 用隔离钥匙串覆盖无项首次写、已有项连续更新、拒绝或超时、写后回读失败。成功时能读回支持范围内的完整凭据；失败时逐字节核对原值，原来无项的也应保持无项。

### A2 · 同邮箱的独立续期凭据被去重后删除

Keychain 和池内为 A，CLI 文件为同邮箱、同到期时间、不同 refresh token 的 A2。切到 B 后，A2 文件消失且池内无副本。两个辅助来源同邮箱也可能过早合并。`readAuxiliaryNativeTokens` 和切换前同步应先比较每个将被改写或清理的来源及版本，再按身份归组。[辅助凭据收集](../src/antigravity-native.ts) · [切换前同步](../src/accounts.ts)

- [ ] 版本相同可以去重，能确认新旧时保留较新版本，无法判断时保留两份并说明冲突。分别测 Keychain A + CLI A2，以及桌面和 CLI 两个辅助来源同邮箱但版本不同。

### A3 · 用户确认到实际写入之间，官方端可能已经换号

用户同意丢弃 CLI 中的 B，后续异步检查共用进程期间，CLI 改为 C，旧确认仍会删除 C。仅改变桌面回退标记的生效状态，也可能改变当前身份。确认应绑定所有待清理来源、凭据版本及影响生效身份的标记状态。[切换指纹](../src/antigravity-native.ts) · [适配器切换](../src/agents/antigravity.ts) · [GUI 入口](../src/main.ts)

- [ ] 通过 GUI 切换入口，在最后一次异步检查期间分别模拟 B 换成 C、单独改变标记生效状态。在首次写入前重新核对；旧确认失效，现场完整保留，用户可重新确认。

### A4 · 切换失败后，旧快照覆盖外部新登录或撤销外部退出

已实测两类情况：AGS 尚未写入、进程检查失败，旧快照仍覆盖新登录；AGS 写完后，官方端重建 CLI/桌面文件或退出 Keychain，此时元数据提交失败，回滚又覆盖外部变化。回滚须逐个来源记录本次实际改动及写入值。[切换异常处理](../src/accounts.ts) · [快照恢复](../src/antigravity-native.ts)

- [ ] 前置检查失败时零写入、零回滚；发生部分写入后，仅撤销 AGS 改动且此后未变的来源。覆盖 CLI 新登录、桌面新登录、Keychain 外部退出、标记变化和恢复操作自身失败。恢复不完整时说明哪一步失败、哪些状态已保留。

### B1 · 繁忙账号仍可能被隔离查询续期

Codex 将完整 refresh token 交给官方 CLI；临时文件设为 `0400` 仍可能发生服务端轮换，而该分支会清理临时副本。待验证更新也是先以 `allowRefresh: true` 发起查询，随后才探测客户端。Windows/Linux 未实现的探测返回空列表。[Codex 查询](../src/agents/codex.ts) · [待验证查询](../src/accounts.ts) · [进程探测](../src/client-logout.ts)

- [ ] 普通刷新和待验证更新均在可能续期的认证启动前作决定。客户端运行或状态未知时，仅使用能保证不轮换的查询路径，否则复用缓存或等待。核对官方端自行续期后能同步、备用账号仍可独立刷新。保留 Antigravity 繁忙时跳过 ACP 的行为。

### B2 · 查到额度后可能删除唯一可恢复的轮换副本

重试返回 `ok` 或命中 `ok` 缓存，只证明 access token 能查额度。它不能证明第一次轮换的 refresh token 已落盘，也不能证明后继凭据可续期。外部凭据验证中还存在官方已轮换、随后额度请求失败就释放临时目录的分支。[提交与重试](../src/accounts.ts) · [Codex 验证](../src/agents/codex.ts) · [Antigravity 验证](../src/agents/antigravity.ts)

- [ ] 只有确认对应代际已持久化，或确有可续期的后继凭据，才清理旧副本。覆盖缓存命中、额度成功但未续期、轮换后额度失败、提交冲突、抛错。无法证明时保留副本，并在最终结果中提供恢复位置。

### B3 · 正常 Codex 凭据无法完成可信替换

验证器删除 `id_token` 后启动官方 CLI。本机 `codex-cli 0.169.0-alpha.11.1` 离线实测：模拟文件带该字段时可读取，省略后反序列化失败。工作区校验还有接受 AGS 预填 `account_id` 的分支；存在 `.pending` 时，提示用户选择的官方重新登录入口也被拦住。[验证输入与身份绑定](../src/agents/codex.ts) · [更新目标](../src/accounts.ts) · [重新登录](../src/isolated-login.ts)

- [ ] 用受支持的官方 CLI 实际读取验证输入。合法同账号、同工作区能完成替换；同邮箱不同工作区、身份不足、验证失败均保留原池和实时登录。用户与工作区须绑定到受服务端认可的凭据。有待验证记录时，也能启动并完成官方重新登录。

### B4 · 退出清理期间接收的关键回存可能被跳过

已用受控时序确认：退出进入异步 `cleanup` 后登记关键回存，退出回调已执行，回存尚未完成。[退出守卫](../src/app-quit.ts) · [回存接入](../src/main.ts)

- [ ] 分别在首次等待、退出确认框、异步清理期间登记回存。应用已接收的关键回存在最终退出前完成安全提交，或留下明确可恢复状态。普通慢速额度查询仍可及时退出。
