# Session 凭据导入

选择一个 JSON 文件或直接粘贴 JSON。文件可以包含一个或多个账号；解析只提取客户端登录需要的字段，不保存导出工具附带的配置、日志、缓存或统计信息。

以下是一种方便整理的格式，`name` 可选，`credentials` 中放完整的客户端凭据：

```json
{
  "accounts": [
    { "name": "日常开发", "credentials": { "tokens": { "access_token": "***", "refresh_token": "***", "id_token": "***", "account_id": "***" } } },
    { "name": "长任务", "credentials": { "tokens": { "access_token": "***", "refresh_token": "***", "id_token": "***", "account_id": "***" } } }
  ]
}
```

这不是唯一允许的结构，也支持：

- 原来的单账号客户端 JSON。
- 直接由多份凭据组成的数组。
- `data`、`accounts`、`credentials`、`auth` 等包装中的凭据，以及嵌套的 JSON 字符串。
- 按账号名称或邮箱组织的对象。
- 同一条目中常见的 `access_token` / `accessToken` 等字段别名。
- 多个完整 JSON 对象直接相连，或通过空行、换行、逗号分隔（包括 JSON Lines / NDJSON）。
- 一个或多个完整的 JSON Markdown 代码块，代码块外只允许空白。
- JSONC 中字符串外的行注释、块注释和对象／数组末尾逗号。
- UTF-8（可带 BOM）及明确带 BOM 的 UTF-16 文件。

优先使用条目中的 `name`、`label`、`nickname` 等名称，缺少名称时使用邮箱前缀；解析后的列表可逐个修改名称、取消勾选。正常的重复账号会跳过；已标记为凭据失效或认证异常的同一账号显示为「更新 · 原名称」，可勾选原位更新，保留原名称、备注和额度历史。不同工作区、不同成员不会仅凭相同邮箱合并。

提交时重新检查账号身份、凭据版本和状态；预览后已恢复的账号跳过，已删除、被替换的更新目标要求重新解析，不会重新创建。新增、更新、跳过重复和无法导入分别汇总。新凭据先标为待验证；Codex 和受支持的 Antigravity 后续查询额度，其他平台仅识别本地凭据。导入同一份已失效凭据不代表登录恢复。备份导入及「本地登录」保存也适用失效账号原位更新规则。

每个账号独立校验。缺少必需 Token、字段类型错误或别名值冲突会显示在对应条目中，其余有效账号仍可导入。不会从不同条目、父子对象或其他账号拼接 Token。来源不明的单段 Session / Cookie 不会自动转换为客户端 OAuth。

解析顺序为标准 JSON 优先，其次才尝试上述明确的包装与分隔形式。分隔器识别字符串、转义符和括号层级，不按花括号的文本位置直接切割；Token 字符串原样保留。

例如，下面两种形式都会识别出两个独立账号，`{ ... }` 代表一份完整凭据：

```text
{ ... }
{ ... }
```

```text
{ ... },
{ ... }
```

不完整括号／引号、同一对象内重复字段、不明分隔符或混杂说明文字会明确报错，不会只取前一段或最后一段。单项字段缺失与语法不完整不同：可明确分隔的条目若只是缺少 Token，其余完整条目仍可导入。

Codex 凭据中的 `auth_mode`、`oauth_provenance`（issuer / client_id）、`login_owner_id` 属于认证字段，会随 Token 保留；合法的 `last_refresh` 时间精度也会保留。导出工具的普通统计字段即使叫 `tokens`，也不会仅凭字段名被误认成账号。

文件上限 32 MB，每次最多 200 个账号，提取后的单个凭据上限 1 MB；过深、过于复杂或反复编码的内容也有限制。未识别的第三方结构可根据上述格式整理。

导入只处理所选账号，不自动切换账号。更新当前账号时，仅在客户端仍使用同一份失效凭据的情况下同步替换；其他账号或客户端已经更换的凭据保持不变。批量写入失败会回滚本批次的新增和更新。预览只向界面传递身份摘要，Token 保留在主进程。

导入成功与客户端可切换是两项能力；各平台当前支持的管理流程见 [账号管理流程](account-management.md)。
